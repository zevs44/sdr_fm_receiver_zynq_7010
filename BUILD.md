# Сборка образа OpenWrt для Antminer S9

Форк репозитория `alexsys87/sdr_fm_receiver_zynq_7010`: пакеты автора + слой сборки
свежего OpenWrt. Что именно изменено относительно оригинала — в [`FORK_CHANGES.md`](FORK_CHANGES.md).

**Что взято у автора без изменений:** проект Vivado (`vivado_2023.2/`), все 19
пакетов из `packages/` (изменены только три файла — см. `FORK_CHANGES.md`),
README. Загрузчик и битстрим — из релиза автора. `nand_install` — идея автора
(его второй проект `Antminer_S9_OpenWRT`), наш пакет её развивает.

Справочные материалы по плате и дизайну — в [`docs/`](docs/README.md): аудиопотоки,
распиновка колодок, пересборка битстрима (на английском и русском).

## Что получается на выходе

`sdcard.img.gz` — образ для SD-карты:

| Раздел | Содержимое |
|---|---|
| FAT, 16 Мб | `boot.bin`, `u-boot.img`, `uEnv.txt`, `system.bit.gz`, `fit.itb` |
| squashfs + overlay | корневая система OpenWrt с пакетами автора |

## Запись на карту

Прошивка платы не требует JTAG: образ пишется на microSD, плата загружается с неё.

**Linux:**

```bash
lsblk                                   # найти карту, проверить /dev/sdX
gunzip -c sdcard-v25.12.6.img.gz | sudo dd of=/dev/sdX bs=4M conv=fsync status=progress
sync
```

`dd` не распаковывает: `gunzip -c` распаковывает образ на лету в канал. Если сначала
записать на карту сам `.gz`, карта не загрузится. Распакованный образ занимает
32 165 812 байт; отдельный файл — `gunzip -k sdcard-v25.12.6.img.gz`.

**Windows — Rufus** (<https://rufus.ie>, переносная версия):

1. Вставить карту, в поле **Устройство** выбрать её.
2. **ВЫБРАТЬ** → `sdcard-v25.12.6.img.gz` (Rufus распаковывает `.gz` сам).
3. Схема раздела — `MBR`, целевая система — `BIOS (или UEFI-CSM)`.
4. **СТАРТ** → подтвердить → дождаться **ГОТОВО**.

**Windows — Win32 Disk Imager** (<https://sourceforge.net/projects/win32diskimager/>):

1. Распаковать образ (`7-Zip` или `gzip -d`): программа не читает `.gz` и `.xz`.
2. **Image File** — распакованный `.img`; **Device** — буква карты.
3. **Write** → подтвердить → **Done**.

После записи Windows может предложить отформатировать карту — откажитесь: это
FAT-раздел с загрузчиком. Запись стирает всё содержимое карты.

## Требования

- Linux или WSL2 (сборка OpenWrt на Windows не поддерживается).
- ~40 Гб свободного места, 4+ Гб RAM.
- Пакеты сборки: `build-essential clang flex bison g++ gawk gcc-multilib g++-multilib
  gettext git libncurses-dev libssl-dev python3 python3-setuptools rsync unzip
  zlib1g-dev file libelf-dev wget ca-certificates ccache`.

## Локальная сборка

```bash
# 1. дерево OpenWrt нужной версии
git clone --depth 1 -b "$(cat .openwrt-version)" https://github.com/openwrt/openwrt.git openwrt

# 2. патчи, фиды, конфигурация
bash scripts/apply.sh ./openwrt

# 3. сборка
cd openwrt
make -j"$(nproc)" download
make -j"$(nproc)" -k world

# 4. проверки (из корня репозитория)
sha256sum -c scripts/expected-artifacts.sha256      # входные двоичные файлы
bash scripts/check_config.sh ./openwrt              # defconfig ничего не исключил
bash scripts/verify_image.sh ./openwrt/bin/targets/zynq/generic   # образ работоспособен
```

Результат: `openwrt/bin/targets/zynq/generic/*.img.gz`.

## Сборка в GitHub Actions

Workflow `.github/workflows/01_build.yml` запускается:

- вручную (`workflow_dispatch`, можно указать тег OpenWrt, пакет и параллельность);
- при изменениях в `packages/`, `target-patches/`, `configs/`, `files/`,
  `bootloader/`, `bitstream/`, `scripts/`, `.github/workflows/01_build.yml`.

Образ и итоговый `.config` выкладываются артефактом `sdcard-<тег>`.
`build.log`, `retry.log`, `.config`, `build-info.txt`, `patch-status.txt` и `openwrt/logs/`
выкладываются артефактом `build-logs-<run_id>` — **всегда**, не только при падении:
без успешного лога не с чем сравнивать.

Сборка идёт как `make -k world`: при ошибке она не останавливается на первом
пакете, а доводит проход и печатает **все** сломанные пакеты. Это экономит
полный прогон (~1,5 ч) на каждый следующий дефект.

`.github/workflows/90_watch-upstream.yml` раз в 6 часов проверяет новые стабильные релизы
OpenWrt: если тег новее, чем в `.openwrt-version`, **сначала проверяет, что патч-слой на него
ложится** (клон тега + `git apply --check` каждого патча), и только потом обновляет файл и
запускает сборку. Если патч не ложится — версия не закрепляется, workflow завершается ошибкой с сообщением:
`.openwrt-version` не укажет на сломанную версию.

`.github/workflows/80_cleanup-runs.yml` раз в сутки удаляет старые **успешные** прогоны
(по умолчанию — `90_watch-upstream.yml`, старше 10 дней), чтобы история Actions не росла
бесконечно. Неуспешные прогоны не удаляются никогда: это история отладки. Параметры
(`workflow`, `older_than_days`, `dry_run`) задаются при ручном запуске; `workflow: all`
чистит все workflow репозитория, включая собственные прошлые прогоны чистки (текущий
прогон не удаляется никогда). GitHub считает workflow по пути файла, поэтому прогоны,
созданные до переименований (`build.yml`, `watch-upstream.yml`, а также `02_watch-upstream.yml`,
`03_cleanup-runs.yml`, `04_qemu-smoke.yml`, `99_watch-upstream.yml`, `02_cleanup-runs.yml`, `03_qemu-smoke.yml`,
`02_qemu-smoke.yml`, `03_release.yml` — два последних были отдельными workflow и вошли в `01_build.yml`), к новым файлам не относятся
и под фильтр по имени файла не попадают — разово их можно удалить с `workflow: all`.

`.github/workflows/01_build.yml` — единый конвейер из четырёх пронумерованных шагов:
`01 lint` → `02 build` → `03 qemu smoke` → `04 release`. Каждый шаг назван номером,
номер стоит и в `name:` и виден в списке прогона: сбой называет свой шаг.
Шаги связаны зависимостями: `02 build` стартует только после успешного `01 lint`
(минута линта не пускает 90-минутную сборку с битым входом), `03 qemu smoke` —
после сборки, `04 release` — последним. По тегу `v*` шаги 02–03 пропущены, поэтому
релиз запускается по `!cancelled()`, а не по успеху соседей: публикация берёт готовый
образ из успешного прогона шагов 01–03, пересборки нет.

### Проверка в QEMU

QEMU — шаг `03 qemu smoke` конвейера: идёт после сборки, берёт её артефакт,
пересборки нет. Перепроверить образ можно, повторив только этот шаг —
прогон сохраняет свои артефакты, повтор их не пересобирает:

```bash
# повторить шаги прогона, завершившиеся ошибкой (обычно это 03 qemu smoke)
gh run rerun <run_id>

# один конкретный шаг: JOB_ID берётся из `gh run view <run_id> --json jobs`
gh run rerun <run_id> --job <job_id>
```

Что делает `scripts/qemu_smoke.sh`: распаковывает образ, дополняет его до 256 Мб
(модель SD в QEMU принимает только размер-степень-двойки), достаёт `fit.itb` из FAT,
вынимает ядро и DTB через `dumpimage`, заворачивает ядро в uImage с адресами `0x8000`
(иначе QEMU грузит голый Image по `0x10000`, а ядро слинковано на `0x8000`), грузит с
DTB и образом в роли SD-карты и ждёт на `ttyPS0` (= второй UART QEMU, `0xE0001000`).
PASS — появился init (`procd: - init complete -`), FAIL — kernel panic или тишина.

**Ограничение:** PL (радио, I2S, антенны) QEMU не эмулирует — проверяется базовая
система (ядро, DTB, squashfs-корень, procd), а не звук. Для звука — только реальная плата.

### Релиз

Шаг `04 release` того же `01_build.yml` публикует GitHub Release из **уже собранного**
образа. Сама она ничего не собирает: находит успешный прогон шагов `01–03` для коммита
тега, скачивает артефакт `sdcard-*`, считает SHA-256 и прикладывает файл к релизу.

```bash
# по тегу (запускается автоматически)
git tag v25.12.6 && git push origin v25.12.6

# вручную: тег и/или конкретный прогон
gh workflow run 01_build.yml -f tag=v25.12.6
gh workflow run 01_build.yml -f release_run_id=<run_id>

# обновить уже существующий релиз
gh workflow run 01_build.yml -f tag=v25.12.6 -f overwrite=true
```

Правила, которые workflow проверяет сам:

- тег обязан начинаться с `v`;
- для коммита тега должен быть **успешный** прогон с артефактом `sdcard-*` (иначе релиз
  не создаётся; прогон по тегу образа не собирает и сам в кандидаты не попадает);
- при явном `release_run_id` проверяется, что прогон успешен;
- существующий релиз не перезаписывается без `overwrite=true`;
- тег с дефисом (`v25.12.6-rc1`) помечается как pre-release.

Тело релиза собирается автоматически: версия OpenWrt, имя файла, размер, SHA-256,
ссылка на прогон и список коммитов с предыдущего тега.

**Важно:** артефакты прогонов живут 30 дней. Если образ нужен дольше — публикуйте релиз.

### Что проверяется до и после сборки

| Проверка | Где | Что ловит |
|---|---|---|
| `shellcheck`, `actionlint` | шаг `lint` | ошибки в скриптах и YAML workflow |
| `scripts/expected-artifacts.sha256` + магия битстрима | шаг «Verify input artifacts» | битый коммит, порча переводов строк, подмена двоичного файла |
| ожидаемые файлы в диффе | шаг «Audit patch layer» | патч лёг частично или не лёг вовсе |
| `scripts/check_config.sh` | шаг «Verify config» | `defconfig` без сообщения исключил пакет или поменял значение |
| `scripts/verify_image.sh` | шаг «Verify image» | образ без битстрима, без kmod, с чужим деревом устройства, без узлов PL в DTB, без `/sbin/nand_install` |
| `scripts/qemu_smoke.sh` | шаг `03 qemu smoke` | ядро не стартует на DTB, корень не монтируется, init не доходит |

Проверки запускаются и локально:

```bash
sha256sum -c scripts/expected-artifacts.sha256
bash scripts/check_config.sh ./openwrt
bash scripts/verify_image.sh ./openwrt/bin/targets/zynq/generic
```

`verify_image.sh` требует `sfdisk`, `mtools`, `dosfstools`, `squashfs-tools`.
Отсутствие битстрима считается провалом: такой образ грузится, но PL остаётся
пустым. Осознанно собрать образ без него: `ALLOW_MISSING_BITSTREAM=1`.

## Загрузчик

`boot.bin`, `u-boot.img` и `uboot_env.bin` **не собираются**: они поставляются
готовыми в `bootloader/` и копируются в образ. U-Boot из OpenWrt 25.12 (версия
2019.07) для этой платы не собирается — поддержка в upstream написана под
U-Boot 2026.04, а FSBL для платы строится в Vitis, а не в OpenWrt.

Поэтому пакет `uboot-zynq` в бэкпорте намеренно исключён. Подробности и
контрольные суммы — [`bootloader/README.md`](bootloader/README.md).

## Битстрим

`bitstream/system.bit.gz` собирается **локально** в Vivado — в CI это невозможно
(лицензия node-locked). Подробности — [`bitstream/README.md`](bitstream/README.md).

Без файла образ соберётся, но PL останется пустым: радио и звук работать не будут.

## Модули ядра и официальные репозитории

**Модули ядра из официального репозитория в этот образ не установятся.** Это не
поломка сборки, а свойство системы пакетов OpenWrt.

Каждый kmod объявляет точную зависимость от пакета `kernel`:

```
EXTRA_DEPENDS := kernel (=$(LINUX_VERSION)~$(LINUX_VERMAGIC)-r$(LINUX_RELEASE))
```

`LINUX_VERMAGIC` вычисляется из конфигурации ядра. Официальные модули собраны с
вермагией `6.12.112-1-ae24847679775ceb14a3d3c24ef38548` — это видно по имени
каталога на `downloads.openwrt.org`. Наша конфигурация отличается: добавлено
устройство и включены свои kmod-пакеты, поэтому вермагия другая, а значит и версия
пакета `kernel` другая.

| Что ставится | Результат |
|---|---|
| kmod из официального репозитория | отказ: невыполнимая зависимость `kernel (=...)` |
| обычный пакет (пользовательский) без kmod-зависимостей | обычно ставится: архитектура `arm_cortex-a9_neon` и musl совпадают |
| пакет, тянущий kmod | отказ по той же причине |

Что делать:

1. **Включать нужные kmod в конфиг сборки** — самый простой путь. Модуль попадёт
   в образ, и ставить его в рантайме не придётся.
2. **Публиковать свой репозиторий kmod.** Сборка создаёт
   `bin/targets/zynq/generic/kmods/<версия-ядра>-<вермагия>/`. Достаточно выложить
   этот каталог и указать адрес в конфигурации пакетного менеджера образа.

Свести вермагию к официальной нельзя: наше устройство само по себе добавляет
символы в конфигурацию ядра.

> В OpenWrt 25.12 пакетный менеджер — **apk** (файлы `.apk`), а не `opkg`.
> Рецепты и команды из старых инструкций (`opkg install`) не применимы.

## Переход на новую версию OpenWrt

Версия задаётся **в одном месте** — файле `.openwrt-version`. Всё остальное
подхватывается автоматически: workflow читает файл, `apply.sh` берёт цель и
подцель из конфига.

| Что | Где | Сейчас | Когда менять |
|---|---|---|---|
| Версия OpenWrt | `.openwrt-version` | `v25.12.6` | при выходе релиза; watcher делает это сам |
| Репозиторий OpenWrt | `01_build.yml` → `env.OPENWRT_REPO` | `https://github.com/openwrt/openwrt.git` | при переходе на форк или зеркало |
| Каталог сборки | `01_build.yml` → `env.OPENWRT_DIR` | `openwrt` | почти никогда |
| Цель / подцель | `01_build.yml` → `env.TARGET` / `env.SUBTARGET` | `zynq` / `generic` | при смене платформы |
| Префикс артефакта | `01_build.yml` → `env.ARTIFACT_PREFIX` | `sdcard` | косметика |
| Таймаут сборки | `01_build.yml` → `timeout-minutes` | `330` | если сборка стала дольше |
| Параллельность make | `01_build.yml` → `env.DEFAULT_JOBS` | `4` (не больше `nproc`) | при OOM — снижать; при большом раннере — поднимать |
| Репозиторий для слежения | `90_watch-upstream.yml` → `env.OPENWRT_REPO` | `openwrt/openwrt` | при переходе на форк |
| Файл версии | `90_watch-upstream.yml` → `env.VERSION_FILE` | `.openwrt-version` | почти никогда |
| Фильтр стабильных тегов | `90_watch-upstream.yml` → `env.STABLE_TAG_REGEX` | `^v[0-9]+\.[0-9]+\.[0-9]+$` | если нужны rc-сборки |
| Цель и устройство | `configs/zynq_antminer_s9.config` | `CONFIG_TARGET_zynq*`, `..._DEVICE_bitmain_zynq-antminer-s9` | при смене платы |

Порядок перехода:

1. Изменить `.openwrt-version` (или дождаться watcher'а — он сам проверит, что патчи ложатся,
   и не закрепит версию, если нет).
2. Запустить сборку вручную: `gh workflow run 01_build.yml`.
3. Если патч не лёг — пересобрать его на новой базе, см. `target-patches/README.md`.
4. Записать изменение в `FORK_CHANGES.md`.

> **Когда бэкпорт `0001` станет лишним.** Поддержка платы ушла в upstream 2026-06-14
> (коммит `e050bb7`) и появится в стабильной ветке после 25.12 — вероятно, в 26.x.
> Как только `target/linux/zynq/image/Makefile` в новой базе уже содержит
> `Device/bitmain_zynq-antminer-s9`, патч `0001` перестаёт ложиться: `apply.sh` упадёт
> с `патч не ложится`. Тогда `0001` удаляется (или из него остаются только DTS-патчи,
> которых нет в upstream), а `0200` пересобирается на новой базе. Шаг «Audit patch layer»
> в `01_build.yml` тоже проверяет файлы, которые создаёт `0001`, — его список нужно
> обновить вместе с патчем.

## Если сборка завершилась с ошибкой

| Симптом | Причина | Что делать |
|---|---|---|
| `патч не ложится на это дерево` | сменилась версия OpenWrt | пересобрать патч на новой базе, см. `target-patches/README.md` |
| `No rule to make target .../system.bit.gz` | патч `0200` не применился | проверить порядок патчей в `target-patches/` |
| пакет автора не собирается | дрейф API ядра или LuCI | править пакет, запись в `FORK_CHANGES.md` |
| `No space left on device` | мало места | освободить диск, `make clean` |
| образ есть, но плата не грузится | нет `boot.bin`/`uEnv.txt` в FAT | проверить, что `apply.sh` отработал без ошибок |
| `Verify config` завершился с ошибкой на `CONFIG_PACKAGE_*` | `defconfig` исключил пакет: нет в фидах или не разрешилась зависимость | смотреть шаг «Verify config», чинить зависимость пакета |
| `Verify image` завершился с ошибкой | собрался, но образ неработоспособен | таблица `PASS/FAIL` в шаге; битстрим, kmod, дерево устройства |
| сборка завершилась с ошибкой, но имени пакета нет | падение на установке пакетов или сборке образа | шаг `Build` печатает последние строки `build.log`; целиком — в артефакте `build-logs-<run_id>` |

Логи сборки: `openwrt/logs/`; в CI они выкладываются артефактом `build-logs-<run_id>`
вместе с `build.log`, `.config`, `build-info.txt` и `patch-status.txt`.
